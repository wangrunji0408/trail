# 衔尾：用身体理解上下文

> 本文面向创作者，包含解谜剧透和技术隐喻。玩家界面、帮助、提示、通关文字中均不出现 agent、LLM、token、context 或 harness 等术语。

## 体验命题

玩家以为自己在玩一款安静的贪吃蛇：吃东西、变长、绕过墙、抵达门。玩到后来才意识到，身体既是一件空间里的物体，也是一份决定接下来能做什么的记录。

核心问题是：**路可以比你的身体长得多，你怎样带着必要的东西走完它？**

参考 Recursed 的方式是让规则始终一致、组合后产生新含义；陶壶真正装着另一座可玩的花园。它不是单纯的传送动画。原型预计体验 10–20 分钟，实际时长需要真人试玩校准。

## 从 harness 提取的骨架

采用主流工具共同的「读取所需信息 → 决定下一步 → 执行 → 接收结果 → 再决定」结构。有限的工作上下文、外部持久状态、压缩和隔离子任务是主要材料，不把某一款产品的全部功能硬塞进同一套规则。

| 游戏中的具体事物 | 技术隐喻 | 玩家如何发现 |
| --- | --- | --- |
| 当前蛇身上的果纹 | 当前上下文中可用的信息 | 曾经吃过但被洗掉的果子，不再能开门。 |
| 有限的果纹槽 | 上下文预算 | 多余金果会挤掉完成目标所需的空间。 |
| 选择小路上的果子 | 按目标选择信息、检索范围 | 最短路线并不总能带上正确的东西。 |
| 三红果 → 一红印 | 压缩与摘要 | 更短的身体仍可通过认红色的门。 |
| 红印没有鲜果汁液 | 摘要的有损性、抽象不保留所有细节 | 前一关学会的好办法，在需要原始细节时会失败。 |
| 写碑、白雨、读碑 | 外部记忆、上下文重置、主动检索 | 刻痕一直存在，但不读回来就不能用于开门。 |
| 向井投果，别处长出月果 | 工具调用与结果回流 | 触发工具后，结果先存在世界里，必须观察/收集后才能影响下一步。 |
| 大蛇留在壶外，小蛇在壶内解谜 | 独立子任务的上下文 | 父任务的记录不自动进入子任务，子任务有自己的容量。 |
| 壶内两果 → 壶外一枚花种 | 子任务返回精炼成果 | 返回时大蛇的原有内容仍在，内部经历不会整段拼接。 |
| 门上可观察的纹样与点亮反馈 | 目标约束、结果验证 | 开门取决于实际状态，不能靠走到出口就宣告成功。 |
| 每步可撤回 | 检查点与探索分支 | 可以比较不同信息选择带来的后果。 |

中性蛇节提供稳定的身体轮廓；有色果纹才占界面显示的容量。果纹代表信息块而非字面上的一个 token。行走没有自动增加一条消息；这是让空间谜题可读的抽象。玩家承担决策过程，规则引擎承担执行环境。原型没有模拟 next-token prediction、概率采样、真实模型推理或注意力权重，也不声称玩家通关就掌握了这些机制。

## 关卡节奏：引入、打破直觉、组合

### 01 · 初尝

一条安全的直线，一颗红果，一扇红门。吃果和门亮起在同一步发生，建立「当前携带的内容决定可执行的动作」这一因果关系。没有自动移动、倒计时或死亡惩罚。

### 02 · 恰好

容量降到两枚。直路上是金果，上路是门所需的红果和月果。贪吃蛇的惯性目标「吃得越多越好」第一次被打破。撞上容量不会破坏状态；撤回始终可用。

### 03 · 折叠

走廊强制吃下三颗红果；门需要红色和两颗月果。三片鳞无法装下五颗果子。花形石台把三颗红果折成一枚红印，腾出两格。此关没有可绕过压缩的路线。

### 04 · 石头记得

白雨切断两侧通路，并洗去果纹。红果只存在于左侧；两块石碑共享刻痕。玩家先写入、穿雨、再读回。石碑存在与蛇身可用是两种不同状态。碑只存最近一枚，避免变成无成本的第二个背包。

### 05 · 井的另一端

重复三红果与石台的视觉配置，但井需要的是鲜果。提前折叠会失去可用输入，玩家可撤回修正。投果后，月果出现在右上角；此刻门仍未点亮。必须绕过去取回结果，形成一次完整闭环。

该关将「压缩丢失任务相关细节」与「外部行动需要接收反馈」放在同一情境中。井的交互提示明确指出缺的是汁液，避免让玩家误以为程序坏了。

### 06 · 壶中天地

红果属于壶外，月果和金果属于壶内。父房间连同蛇的位置、果纹、剩余物件被整体保存。进入时创建空白子房间；通过壶内门后，只返回花种并恢复父房间。撤回返回动作可以准确回到刚刚的壶内。

目前是一层真实嵌套，不宣称实现了任意递归或多蛇并行。壶内小关保持简单，让理解状态边界成为这关的主要难点。

### 07 · 花园深处

不再添加规则。三鲜果 → 红印 → 写碑 → 穿雨 → 读回 → 入壶取花种 → 取月果 → 三纹开门。此门明确需要红印，而非任意红色，玩家需要在过雨之前完成折叠。结尾只说「你带着的很少。你走过的很远。」不出现技术揭底。

## 公平性与呈现

- 果子使用颜色和形状双重编码；门、身体、容量条共用同一图形。
- 每个重要状态变化都给出世界内的一句话，不显示调试日志或术语。
- 每关三层提示：观察方向、机制线索、具体行动。玩家主动展开。
- 失败动作不改变棋盘或步数；所有合法动作，包括写入与进出陶壶，都可撤回。
- 默认静音，可打开合成短音；支持减少动态效果偏好。
- 手机的方向键与空格按钮和键盘驱动同一状态引擎。
- 庭院手记可自由选关，方便试玩反馈；默认「下一座」引导顺序学习。
- 局部关卡状态只在内存中；localStorage 仅存关卡进度。

## 与参考项目的关系

查阅日期：2026-09-06。机制为跨产品的设计提炼，不表示各个 harness 的功能完全一致。

1. [OpenAI：Compaction](https://developers.openai.com/api/docs/guides/compaction)。压缩以更少的上下文承接后续所需状态；真实压缩结果可能是不透明的对象。红印是可视化教学抽象，并不等同于某种实际摘要格式。
2. [Claude Code：How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works)。明确描述 gather context / take action / verify results 循环、工具结果回流、上下文容量、压缩、持久记忆和独立子任务上下文。石碑、井和陶壶分别提炼其中的状态关系。
3. [pi：coding-agent README](https://github.com/earendil-works/pi/tree/main/packages/coding-agent)。原 `badlogic/pi-mono` 链接在查阅时重定向到此仓库。文档描述有损压缩，完整历史保留在 JSONL 中并可通过树形会话回访；这启发了「当前可用内容」与「外部保留历史」的区别。
4. pi 的核心明确不内建 sub-agents、MCP 或 permission popups，允许通过扩展/其他实例组织这些能力。因此陶壶借鉴的是独立任务上下文的一般模式及 Claude Code 的说明，不能被宣传成 pi 内建能力。

## 下一轮验证与扩展

先观察真人是否能在第四关区分「石头里有」与「身上有」，以及第五关是否主动去拾取井的回应。需要记录的是错误推断和顿悟时刻，而不是点击量；本原型不收集遥测。

当前谜题偏机制教学，路径优化难度较低。下一轮可增加「隔很久才需要的具体细节」来检验摘要选择，增加两座不同任务的壶来体现任务范围，再考虑可携带陶壶或多层嵌套。指令层级、不可信外部文字、工具授权、随机生成等议题应各自获得独立关卡，不宜用一个变色机关笼统代替。

## 验证

`npm test` 对七个主庭院逐步执行真实合法解，确保没有跳状态或穿墙；另外验证容量阻挡、有损转换、刻痕跨白雨保留、调用后结果仍未入身、父子上下文隔离、跨房间撤回、重置与通关状态。浏览器还需验证键盘、触屏、弹窗、页面缩放及 GitHub Pages 子路径加载。
